============================================================
 プロジェクト概要（使っている技術・コードの中身・選んだ理由）
============================================================

ゲーム名：BRAVER（二刀流の3Dアクション）
流れ　　：タイトル → ゲーム → クリア / ゲームオーバー → タイトル

各項目は次の3つで書いています。
  【何か】  その技術・仕組みが何をしているか
  【理由】  なぜ使っているか
  【比較】  他の選択肢と、その中からこれを選んだ理由
※「もともと入っていた」と書いたものは、プロジェクトの土台として最初から用意されていたもの。


============================================================
 1. 開発の土台
============================================================

■ C++20 / Visual Studio / Windows
  【何か】  ゲーム全体を C++ で書き、Visual Studio でビルドしている。
  【理由】  処理が速く、DirectX を直接使えるため。
  【比較】  C#（Unity）・Blueprint（UE）などもあるが、このプロジェクトは
            「ゲームエンジンを使わずに自分で作る」形のため C++ を使う。
            C++20 は std::lerp・std::clamp など便利な機能が使えるので採用。

■ DirectX 11（描画）
  【何か】  3D・2D の描画をすべて DirectX 11 で行っている。
  【理由】  Windows で最も情報が多く、扱いやすい描画の仕組みのため。
  【比較】  DirectX 12 / Vulkan は速いが、書く量がとても多く難しい。
            OpenGL は Windows 専用の機能と相性が悪い。
            学びやすさと必要十分な性能から DirectX 11。

■ KdFramework（もともと入っていた）
  【何か】  DirectX の面倒な部分をまとめた土台。
            モデル読み込み・シェーダー・当たり判定・アニメーション・
            フォント・音・エフェクトなどの機能がある。
  【理由】  土台を一から作らずに、ゲームの中身に集中できるため。
  【比較】  自分で全部作ることもできるが、時間がかかりすぎる。
            必要な所だけ直しながら使っている（下の「フレームワークの修正」参照）。


============================================================
 2. 使っているライブラリ
============================================================

■ DirectXTK（SimpleMath・Audio）（もともと入っていた）
  【何か】  Math::Vector3 / Matrix / Quaternion などの計算用の型と、音の再生。
  【理由】  ベクトルや行列の計算を短く書けるため。
  【比較】  DirectXMath だけでも計算できるが、書き方が長く読みにくい。

■ DirectXTex（もともと入っていた）
  【何か】  PNG などの画像をテクスチャとして読み込む。
  【比較】  stb_image なども使えるが、DirectX 向けの形式に直接変換できるのでこちら。

■ tinygltf（もともと入っていた）
  【何か】  glTF 形式（.gltf / .bin）の3Dモデル・アニメーションを読み込む。
  【理由】  glTF は中身が分かりやすい公開された形式で、UE から書き出せるため。
  【比較】  FBX は情報が多いが、読み込みに専用の SDK が必要で重い。
            glTF なら中身（骨の名前・アニメーションのキー）を自分で調べられ、
            不具合の原因を数値で確かめられた（剣が斜めに飛ぶ件など）。

■ Effekseer
  【何か】  斬撃・ヒット・撃破などのエフェクトを再生する。
  【理由】  専用ツールで作ったエフェクトを、そのままゲームで再生できるため。
  【比較】  パーティクルを自作することもできるが、見た目を作るのに時間がかかる。
            Effekseer は無料・日本語の情報が多い・DirectX 11 に対応しているので採用。

■ Dear ImGui（もともと入っていた）
  【何か】  ゲーム中に表示するデバッグ画面（Player Parameter Editor）。
  【理由】  ゲームを止めずに数値を変えて、すぐ見た目を確認できるため。
  【比較】  数値をファイルに書いて再起動する方法もあるが、調整に時間がかかる。


============================================================
 3. モデル・アニメーションの準備（UE → glTF）
============================================================

■ Unreal Engine 5.4 でリターゲット → glTF で書き出し
  【何か】  Dual_Sword のアニメーションを、キャラクター（SK_Assassin）の体に合わせて
            作り直し（リターゲット）、glTF で書き出してゲームで読み込む。
  【理由】  アニメーション素材とキャラクター素材が別々の販売物で、骨の作りが違うため。
  【比較】  Blender でもリターゲットできるが、どちらの素材も UE 用なので、
            UE の IK Retargeter を使うのが一番きれいに移せる。
  補足：  作業を Python スクリプト（Tools/UE/）にして、手作業のミスを減らした。
          剣の骨は元（Weapon_R）と先（weapon_r）で名前と作りが違うので、
          専用のチェーンで対応づける必要があった。


============================================================
 4. コードの全体の作り
============================================================

■ シーン管理（SceneManager・BaseScene）
  【何か】  タイトル・ゲーム・クリア・ゲームオーバーの画面をクラスに分け、
            SceneManager が「今の画面」を切り替える。
  【理由】  画面ごとの処理を混ぜずに、別々に作れるため。
  【比較】  1つのクラスで if 文で画面を切り替えることもできるが、画面が増えると読めなくなる。

■ ゲームオブジェクトのリスト（KdGameObject）
  【何か】  プレイヤー・敵・地面・UI など、全部を同じ親クラスで作り、
            シーンのリストに入れて、毎フレーム順番に Update・描画する。
  【理由】  「リストに入れるだけで動く」ので、新しい物を追加しやすい。

■ キャラクターの共通部分（BaseChara）
  【何か】  プレイヤーと敵で共通の処理（アニメーション・重力・地面判定・
            押し出し・HP・ルートモーション）をまとめた親クラス。
  【理由】  同じ処理を2回書かないため（直す時も1か所で済む）。

■ ステートパターン（PlayerState・EnemyState）
  【何か】  「待機」「走り」「攻撃」「回避」「ジャンプ」など、状態ごとにクラスを分け、
            今の状態のクラスの Update だけを動かす。
  【理由】  状態ごとの処理と、状態の切り替え条件が1か所にまとまり、分かりやすい。
  【比較】  enum と switch 文でも作れるが、状態が10個以上あり、
            1つの関数がとても長くなるので、クラスに分ける方法を選んだ。

■ バトルモードと ATB ゲージ（FF7リメイクのクラウド風）
  【何か】  E キーで「オペレーター（速い）」と「パニッシャー（遅いが重い）」を切り替える。
            攻撃を当てる・時間がたつと ATB ゲージ（2本）がたまり、
            1キー（ゲージ1本）・2キー（ゲージ2本）でアビリティ（攻撃04・05）を出す。使った後は CT がある。
            プレイヤーは常に剣を抜いた状態にし、剣を納める処理とアニメーションはプログラムから削除した
            （アニメーションのファイルはフォルダに残してある）。
  【理由】  通常攻撃 → ゲージがたまる → 大技、という「攻める理由」と、
            モードの使い分けで戦い方に変化をつけるため。
  【比較】  FF7R のように「コマンドメニューを開いて技を選ぶ」方法もあるが、
            アクションの気持ちよさを優先し、キーで直接出す方法にした。
  （詳しくは Docs/ATBSystem.txt）

■ ヒットストップ（HitStop）
  【何か】  攻撃が当たった瞬間に、プレイヤーと敵を数フレームだけ止め、カメラを少し揺らす。
            ゲーム全体で1つの仕組みにして、すべての攻撃（敵の攻撃・ガードも）に同じルールでかける。
            普通 4フレーム、クリティカル 7フレーム、パニッシャー・アビリティは +2フレーム。
  【理由】  当たった「手ごたえ」が出て、攻撃が気持ちよく見えるため。
  【比較】  攻撃ごとに止める処理を書くと、攻撃を増やすたびに書き忘れが起きる。
            当たり判定（AttackOBB）の中でかけるようにして、全部に自動でかかるようにした。

■ シングルトン（SceneManager・KdEffekseerManager など）
  【何か】  1つしか無いもの（画面管理・エフェクト管理など）を、どこからでも使えるようにする。
  【比較】  便利だが使いすぎると依存関係が分かりにくくなるので、管理役だけに使っている。

■ 時間の数え方（フレーム数）
  【何か】  「30フレーム後」のように、時間をフレーム数で数えている（60フレーム ≒ 1秒）。
  【理由】  アニメーションのキー（60fps）や、攻撃の当たるフレームと合わせやすいため。
  【比較】  経過秒数（deltaTime）で数えると処理落ちに強いが、
            フレーム指定の調整がしにくくなるので、今はフレーム数のまま。


============================================================
 5. アニメーション
============================================================

■ アニメーションの再生とブレンド（KdAnimator）
  【何か】  キー（時間ごとの骨の位置・回転）を補間して骨を動かす。
            切り替える時は、前と次のアニメーションを数フレームかけて混ぜる。
  【理由】  急に切り替わると姿勢がパッと変わって不自然なため。

■ キーの無い骨は「初期姿勢」（ResetPoseToRest・Interpolate）
  【何か】  UE から書き出したファイルは、動かない骨のキーが省かれている。
            キーが無い骨は、モデルの初期姿勢を使う。
  【理由】  0 で埋めると体が潰れ、前のアニメーションの値を残すと姿勢がおかしくなるため。

■ 骨を名前で対応づけるリターゲット（RetargetAnimation）
  【何か】  アニメーションとモデルで骨の並びが違っても、骨の名前で対応づけて再生する。
  【理由】  骨の並び順に頼ると、モデルを差し替えた時に全く違う骨が動くため。

■ ルートモーション（腰の移動を取り出す）
  【何か】  アニメーションで腰が前に進んだ分だけ、キャラクター自体を動かし、
            腰はキャラクターの位置に固定する。
  【理由】  アニメーションが切り替わるたびに体が元の位置に戻るのを防ぎ、
            足の動きと移動の速さを一致させる（足が滑らない）ため。
  【比較】  ・その場で動くアニメーション＋プログラムで移動：簡単だが足が滑る。
            ・root の骨の動きを使う：今回の素材は root に動きが入っていなかった。
            → 腰（pelvis）の水平の動きを使う方法を選んだ。
            ジャンプだけは「踏み切った時の勢い」をプログラムで引き継ぐ
            （物理的な放物線と合わせるため）。

■ 着地のタイミング合わせ
  【何か】  着地アニメーションの「両足が地面に着くフレーム」を事前に調べ、
            地面に着く瞬間にそのフレームになるよう、着地アニメーションを早めに始める。
  【理由】  着地した後で着地アニメーションを始めると、足が浮いて見えるため。

■ 剣を投げる攻撃（5-2）の向きの補正
  【何か】  投げた剣が一番遠くまで飛ぶ向きを調べ、まっすぐ前に飛ぶように回して補正する。
  【理由】  アニメーションのデータで剣が斜めに飛んでいたため（リターゲットし直した後は、
            補正の角度が自動で 0 に近くなり、ほぼ効かない）。


============================================================
 6. 当たり判定
============================================================

■ KdCollider（もともと入っていた）を使った3種類の判定
  ・地面　　：足元から下へのレイ（光線）。地面に立たせる・着地を予測する。
  ・押し出し：球。キャラ同士・壁にめり込まないようにする。
  ・剣　　　：OBB（向きを持った箱）。剣の刃に沿った細長い箱で、敵の当たり判定と調べる。
  【比較】  剣を球にすると、細長い刃の形に合わない。
            カプセルでもよいが、フレームワークに OBB があったので OBB を使った。

■ 剣の刃の向き・長さを自動で求める（主成分分析）
  【何か】  剣のモデルの頂点が一番長く並んでいる向きを計算し、それを刃の向きとする。
  【理由】  モデルを差し替えても、手で数値を調整せずに判定の箱が刃に合うため。
  【比較】  手で位置と角度を調整する方法（Weapon Adjust）もあるが、
            モデルを変えるたびに調整し直しが必要になる。

■ 当たった後の無敵時間
  【何か】  敵は攻撃を受けると 30 フレーム無敵になる。
  【理由】  剣が毎フレーム当たり続けて、ダメージやエフェクトが何十回も出るのを防ぐため。


============================================================
 7. 見た目の演出
============================================================

■ 剣の軌跡（KdTrailPolygon）
  【何か】  刃の根元と先端の位置を毎フレーム記録し、つないだ帯を描く。
            フレームの間は Catmull-Rom 曲線で補間し、きれいな弧にする。
            帯の絵はプログラムで作り、加算合成（色を足す）で光らせる。
  【理由】  加算合成は光の表現に向いていて、黒い部分は透明に見えるため。
  【比較】  半透明で描く方法もあるが、このシェーダーは透明度 55% 未満を描かないため、
            ぼかした部分が消えてしまう。そのため明るさで薄さを表す加算合成にした。

■ ヒットエフェクト（Effekseer）
  【何か】  攻撃が当たった位置に、攻撃の種類ごとのエフェクトを出す。
  【理由】  当てた手応えを出すため。振るたびに出すと、敵がいなくても出て重くなるため、
            当たった時だけにした。

■ カメラ（TPSCamera）
  【何か】  マウスで回せる三人称カメラ。壁があればカメラを手前に寄せる。
            高さは「足元の高さ＋立っている時の腰の高さ」になめらかに付いていく。
  【理由】  腰の骨の高さに付いていくと、回避で腰が下がった時にカメラがガクンと動くため。


============================================================
 8. 2D・タイトル画面
============================================================

■ 文字の表示（UIText・KdFont）
  【何か】  Windows の文字の形（GDI）からテクスチャを作り、2Dで描く。
            タイトルロゴは用意したフォント（Asset/Font/Y224.ttf）を読み込んで使う。
  【理由】  ゲーム用のフォントを同梱すると、どの PC でも同じ見た目になるため。
  【比較】  文字を画像で用意する方法もあるが、文字を変えるたびに画像を作り直すことになる。

■ タイトル画面の演出
  【何か】  背景でキャラが技を見せ続け、カメラがゆっくり動き、火の粉が舞い、
            ロゴやメニューが時間に合わせて現れる。
  【使っている考え方】
    ・sin（行ったり来たりする値）で、カメラや光をゆらゆら動かす
    ・イージング（最初は速く最後はゆっくり）で、動きを自然にする
    ・光の玉・四隅を暗くする画像は、プログラムで1ピクセルずつ作る
  【理由】  画像ファイルを用意しなくても演出が作れ、数値で調整しやすいため。


============================================================
 9. 入力・データ・デバッグ
============================================================

■ キー入力（InputHelper::KeyTrigger）
  【何か】  「押した瞬間」だけを判定する。
  【理由】  押しっぱなしでメニューが連続で動いたり、攻撃が連続で出たりしないため。
  【先行入力】プレイヤーの攻撃・回避・ジャンプ・アビリティは、押してから10フレームの間は
            「押された」ことを覚えておく。技の終わり際に少し早めに押しても受け付けるので、
            操作の反応が良くなる（アクションゲームでよく使われる方法）。

■ 調整用データ（Asset/Data/）
  ・PlayerParams.txt　：回避の速さ、攻撃ごとの当たるフレーム
  ・WeaponParams.json ：武器の位置・角度
  【理由】  プログラムを書き換えずに、デバッグ画面から調整して保存できるため。
  【比較】  JSON ライブラリを使う方法もあるが、項目が少ないので自分で読み書きしている。

■ デバッグ画面（Player Parameter Editor）
  ・攻撃パラメータ、回避の速さ、走る速さ、武器の位置の調整
  ・ルートモーション・剣の判定の向きを切り替えて見比べるチェックボックス
  ・赤い箱（攻撃判定）・緑の線（敵の判定）の表示

■ Git / GitHub
  【何か】  変更の履歴を残し、Visual Studio の Git 画面でプル・プッシュする。
  【理由】  おかしくなった時に、前の状態に戻したり、どの変更が原因か調べたりできるため。


============================================================
 10. フレームワークに加えた修正（主なもの）
============================================================

  ・KdStandardShader：モデルの中のメッシュごとに、スキンメッシュかどうかを切り替えて描く
                      （剣が手に表示されない不具合の修正）
  ・KdAnimation　　 ：キーの無い成分（位置・回転・拡縮）は元の値を使う
                      （体が潰れる不具合の修正）
  ・KdGLTFLoader　　：1つの頂点に骨が8本まで影響する UE のモデルを、上位4本にまとめる
  ・KdFont　　　　　：作成済みの文字の幅も文字列の幅に加える（中央揃えのずれの修正）、
                      文字セット・文字幅を指定できるようにする（Y224 フォント対応）
  ・KdSpriteShader　：文字の描画関数を外から使えるようにする
